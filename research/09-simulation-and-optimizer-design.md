# 09 — Simulation & Optimizer Design

This is the synthesis file: it does not introduce a new FGO subsystem to source (files 01–08 already cover every mechanic), it defines **how those mechanics compose into one turn-by-turn simulation engine**, and **what search strategy sits on top of it** to deliver the 3T Farm Optimizer, the ST Burst Finder, the Manual/Sandbox mode, and the "Not Clearable Yet" Gap Analysis (`00-project-overview.md` §1). Two genuinely new primary-source lookups were needed to close open items explicitly deferred to this file (Master-level→Cost table, `criticalWeight`'s schema location) — both done via the Atlas Academy API this session and cited in §6. Everything else in this file is **architecture derived from files 01–08's already-cited mechanics**, not new game-data claims.

---

## 1. Simulation state model

The simulator is a pure function `(BattleState, Action) → BattleState'` applied repeatedly — this is what makes the same core serve both the optimizer (search over `Action` sequences) and the Manual/Sandbox mode (`00-project-overview.md` §1.3 — user supplies the `Action` sequence directly, no search).

**`BattleState`** — everything that can change during a fight:
- `waves: Wave[]`, current wave index, current turn number (generalized N-wave/M-turn scope, §5 of file 00).
- `enemies: EnemyInstance[]` per current wave — each is a live copy of a `QuestEnemy` (file 08) plus **mutable** fields: current HP, active buff instances (with remaining `Turn`/`Count`, file 05 §7), and a `shift`/`call` pending-swap flag (file 01/08 §4).
- `servants: ServantInstance[]` (3 front-line + up to 3 sub-member, file 00 §4 "front-line vs sub-member") — each a live copy of the user's account-entered `NiceServant` + skill levels + NP level + CE + append skills (file 00 §3 "Stats at actual level"), plus mutable: current HP, current NP gauge (in `FULL_TD_POINT` units, file 04), active buff instances, skill cooldown counters, Command Seal count remaining, stars-on-hand (carried into the servant's currently-held cards, file 04 §6).
- `handCards: Card[]` — the current turn's drawn 3-servant×5-card pool minus already-played cards (file 00 §4 "Card draw / hand mechanics" — a distinct RNG surface, §3 below).
- `starsCarried: number` — the pool of crit stars generated during the previous turn's attack phase, allocated via the file 04 §6.2 weighted lottery to determine the *current* turn's per-card crit chance. **No cross-turn accumulation/cap needed** (file 04 §6.3, follow-up pass): any stars not "spent" toward the current turn's crit-chance rolls are discarded, not carried to a third turn — so this field only ever needs to hold one turn's worth of leftover stars at a time, never an unbounded/accumulating pool.
- `fieldTraits: Trait[]` — the quest's terrain trait(s) (file 06 §1, e.g. `fieldForest`), static for the whole quest.
- `costSpent`/`costBudget` — running total for the party actually fielded (file 00 §3 "Master level / Cost budget").
- `log: ActionRecord[]` — append-only history, needed for both the per-hit/per-card fine-grained breakdown and the rolled-up per-wave summary (`00-project-overview.md` §1.1).

**`Action`** — one atomic thing a turn's plan can do, matching the granularity the user needs for Manual/Sandbox mode (file 00 §1.3) and what the optimizer searches over:
`useSkill(servant, skillSlot, target?)`, `useMysticCodeSkill(slot, target?)`, `orderChange(outgoing, incoming)`, `playCard(handCardId)` (three per turn, in chosen order — file 00 §4 "same-turn NP-order effects"), `castNp(servant)` (resolved in card-chain position per file 03), `useCommandSeal(effect)`, `endTurn()`. Every `Action` is resolved **strictly in sequence**, never batched — this is the direct engine requirement file 00 §4 already derived from Space Ishtar's intra-NP function-order finding and the "same-turn NP-order effects" entry: the evaluator must re-check buff/gauge/HP state before resolving the next `Action`, not snapshot state once per turn.

## 2. Turn-resolution pipeline (composing files 02–08 into one ordered algorithm)

For a single `playCard`/`castNp` action, the pipeline is, in order:

1. **Pre-action state check** — is the target dead/shifted/spawned-in this action (enemy `shift`/`call` resolution from a *previous* action, file 08 §4)? Re-resolve target list.
2. **Resolve the card/NP's function list in array order** (file 00 §4 "Intra-skill/NP function execution order") — each function may itself grant a buff that the *next* function in the same activation reads, so this must be a strict sequential fold, not an all-at-once apply.
3. **For each hit in the card's/NP's `hitsDistribution`/`npDistribution` array** (file 00 §4 "Hit count mechanics", file 03):
   a. Roll/derive **crit** for this hit if applicable (stars-on-hand → per-card crit chance via `CRITICAL_RATE_PER_STAR`, file 04 §6; NP cards never crit, file 03).
   b. Compute damage via the file 02 master formula (14 multiplicative terms + 3 additive terms), pulling: card-type base modifier, NP multiplier + Overcharge stage (file 02/04), class attack rate + class triangle (file 06 §3–4), attribute triangle (file 06 §5), all active buff-action sums (file 05 §2, clamped by `maxRate`), crit modifier (2.0× + buffs, file 03), defense-side DEF%/Guts/Invincible/Evade checks (file 05 §6/§9 below) — **Evade and Invincible are resolved before the damage formula even runs** (an evaded hit deals no damage and, per file 00 §4's still-open item, may or may not grant gauge/stars — flagged in §7).
   c. Apply Overkill check per-hit (file 02: not a damage multiplier; only feeds NP-gain ×1.5 and star +30pp, file 04 §6).
   d. Apply the hit's own crit-star drop (`starGen` + `addCritical`/`adjustCritical` + flat crit/overkill bonuses, file 03) and NP-gauge gain (attacking formula, file 04) — both **per hit**, not per card, which is exactly why file 00 §4 called hit-count-and-distribution a first-class datum.
   e. Subtract HP from every hit target; check death → resolve `shift`/`call`/Guts (file 08 §4, file 00 §4 "Guts") before moving to the next hit.
4. **Post-card bookkeeping**: brave-chain/chain-position bonus if this completes a 3-card chain (file 03), skill cooldown ticks are **not** per-card (they tick at `endTurn()`), buff `Turn`/`Count` decrements happen at the points file 05 §7 specifies (start/end of turn or per-consumption, per buff).
5. **`endTurn()`**: decrement all `Turn`-based buff/cooldown counters, resolve any "gauge gain from taking damage" (defending formula, file 04) if enemy-attack simulation is ever turned on (currently out of scope, file 00 §2), draw the next turn's 5-card hand (§3 below), and recompute overcharge-eligibility/gauge caps for the next turn.

This pipeline is deliberately the **single execution path** for both the optimizer's simulated candidate lines and the user's own Manual/Sandbox plan (file 00 §1.3) — there is no separate "fast approximate" path for search and "accurate" path for the final report; the search just calls this same function many times.

## 3. RNG surfaces and probability-of-clear

File 00 §3 commits to modeling probability, not just deterministic damage. Three independent RNG surfaces feed into that probability, each already sourced in files 03/04:

- **Card draw** (file 00 §4): which 5 of the fielded servants' 15 cards appear as choices each turn. No primary source found this session (or prior) for the exact weighting/guarantee rule (e.g. "at least one of each type") — this remains genuinely open (see §7) and is the single biggest gap for exact chain-probability modeling. Until sourced, the engine should expose this as a **configurable draw-model parameter** (uniform random vs. a guaranteed-one-per-type heuristic) rather than hardcoding an unverified assumption, and flag probability outputs as approximate when the draw-model is unconfirmed.
- **Crit-star allocation & crit roll** (file 04 §6): fully sourced — per-hit star generation, weighted per-card allocation, `CRITICAL_RATE_PER_STAR`. This one can be modeled exactly (Monte Carlo or closed-form binomial-style approximation over the known weights).
- **Debuff application MISS/GUARD roll** (file 05 §6.3 formula) — relevant when a plan's damage depends on a prior debuff (e.g. a DEF-down needed to reach lethal) actually landing.

**Recommended approach**: run the deterministic "expected value" pass first (fast, used for search/pruning — §4), then for the Top-N candidates that survive pruning, run a Monte Carlo pass (thousands of simulated turns varying the card draw and crit/debuff rolls) to produce the actual `"clears in 3T with probability X%"` figure the user sees (file 00 §1.1). This two-tier approach avoids paying Monte Carlo cost for the entire search space, only for finalists.

## 4. Search / optimizer strategy

**Search space** (per file 00 §3 "Search scale"): `{candidate servant subset (≤6, user-shortlisted)} × {CE assignment per slot, respecting owned-copy counts, file 00 §3} × {skill-usage plan per turn} × {card-play order per turn} × {Order Change timing}`. This is combinatorially large even after user shortlisting, so:

- **Coarse pruning pass (deterministic, no RNG)**: for each candidate servant subset + CE assignment, compute a fast upper-bound total damage/NP-gauge trajectory using the deterministic pipeline (§2/§3) with a small number of "obviously reasonable" skill/card orders (e.g. always skill-then-NP, buster-loop and arts-loop heuristics as seed strategies — file 00 §3 explicitly wants known strategies to *emerge*, not be the only options considered, so these seed heuristics widen rather than restrict the search: any subset whose *best seed-heuristic result* clearly misses the turn target by a wide margin is dropped before deeper search, but every subset still gets at least the seed pass, not just pre-approved archetypes).
- **Fine search on survivors**: permute skill-order/target/card-order more exhaustively only for subsets that passed the coarse filter — this is where genuinely non-obvious lines (not matching a named community strategy) get discovered.
- **Objective functions** (file 00 §1.1), each a distinct sort key over the same candidate pool rather than a separate search:
  - Default: minimize turn count, tie-break by safety margin (probability of clearing within that turn count) and then by leftover damage/overkill margin.
  - **Minimum Cost mode**: sort candidates by total party Cost (servants' + CEs' `cost` fields, §6) among those that still clear within the target turn count — a re-sort of the same search results, not a different search.
  - **Prefer Event CE / Prefer Bond CE modes**: bias CE *assignment* within a fixed servant subset toward event-drop-up/Bond CEs per-slot with fallback (file 00 §1.1), then re-run the deterministic pass for that assignment — this is a modification to the CE-assignment axis of the search space, applied before the coarse pruning pass, not a post-hoc filter.
  - **Preferred-attacker constraint**: restrict the search to candidate subsets where the pinned servant is assigned the "main attacker" role (defined as: the servant whose NP/burst is the one required to bring a target below the lethal threshold in the winning line, not merely present) — if the constrained search space yields no viable line, re-run unconstrained and surface that result explicitly labeled as a fallback (file 00 §1.1's "Fallback suggestion" requirement).
  - **Top-5 diversity**: after ranking, deduplicate near-identical lines (same 3 core servants, trivially reordered sub-slots) so the 5 reported results are meaningfully different strategies, not 5 permutations of the same one.
- **Core vs. free-slot tagging** (file 00 §1.1): once a winning line is found, mark exactly the servants whose actions appear in the executed plan (dealt damage, provided a buff actually consumed, or held a role like Order Change bench-fodder that the plan specifically relies on) as **core**; any of the remaining up-to-6 party slots the plan never references are **free**, reported as "bring whatever you want" with the remaining Cost budget shown (`costBudget - costSpent`, §1/§6).

## 5. ST Burst Finder as a specialization, not a separate engine

File 00 §1.2/§5 requires multi-turn setup support for the burst finder, not just single-turn max-damage. This falls out of the same engine with a different **objective + horizon**, not new mechanics:

- **Objective**: maximize single-target damage delivered to one specific enemy by a chosen turn, rather than "clear all waves in minimum turns."
- **Multi-turn setup horizon**: the search space's turn dimension is not capped at 1 — a 2-turn plan (turn 1: buff-stack/NP-charge/kill a *specific* lower-priority enemy to trigger a `call`/reinforcement or unblock a target, per file 08 §4's `call` mechanism; turn 2: execute the burst) is a first-class search candidate, found the same way a 3T-clear line is found: simulate turn 1 fully (including its consequences — new enemy via `call`, Order Change availability), then search turn 2 from the resulting `BattleState`.
- **Bait-then-burst (count-based Evade/Invincible)**: this is literally "spend `playCard`/`castNp` actions on a non-primary target/attacker first, observe the Evade/Invincible buff's `Count` decrement in the resulting `BattleState` (file 05 §9-equivalent field), then sequence the real burst action once `Count` reaches the point the buff is consumed" — no special-case logic beyond the engine already tracking `Count` per buff instance (already required by file 05 §7) and letting the search consider "waste an action on the defended target" as a legitimate `Action`.
- **Guts-aware lethality threshold**: the "is this enough damage" check for the burst finder must sum current-bar HP **plus every stacked Guts revival's HP amount** (file 00 §4 "Guts"), not just current HP — computed once per candidate enemy from its passive/skill Guts buffs (file 01/08), not assumed.

## 6. Newly-closed open items (primary-source lookups done this session)

Two items file 00 explicitly deferred to file 09 were resolved via direct Atlas Academy API calls this session:

- **Master-level → Cost table**: `https://api.atlasacademy.io/export/JP/NiceUserLevel.json` is confirmed live — a flat object keyed by Master level (`"1"`, `"2"`, ...), each entry giving `requiredExp`, `maxAp`, **`maxCost`**, `maxFriend`. This directly answers file 00 §6's "exact Master-level-to-max-Cost table" question: the engine reads the user's entered Master level, looks up `maxCost` from this table, and that is `costBudget` in §1's `BattleState` — no derivation needed. Per-unit Cost is confirmed to be a plain integer field directly on the nice servant/CE object (live-checked: Mash Kyrielight `cost: 0` — a deliberate exemption, since Mash is mandatory-fielded and Atlas Academy's own data reflects that; a 5★ CE like Kaleidoscope `cost: 12`) — `costSpent` in `BattleState` is simply the sum of `servant.cost + equippedCe.cost` across the fielded 6 slots, confirming file 00 §3's Cost-budget decision is directly implementable with no missing field.
- **`criticalWeight`'s schema location** (file 04 §6.3 flagged this as unresolved after three research passes): confirmed this session to live on the **per-ascension `mstSvtLimit` record** (`limitCount: 0` ascension stage on Mash Kyrielight: `criticalWeight: 99`). **Correction from a follow-up pass**: this field *is* also surfaced via the `/nice/` endpoint after all, under the name `starAbsorb` — live-verified identical (`NiceServant.starAbsorb` = 99 for Mash, matching `mstSvtLimit.criticalWeight` = 99 exactly) — the claim below that only `/raw/` exposes it was incomplete; the engine should read `NiceServant.starAbsorb` directly rather than hitting `/raw/`. The **weighted star-to-card allocation formula itself** (how `criticalWeight`/`starAbsorb` combines with the shuffled +50/+20/+20 base-slot bonus and Star Focus buffs, file 04 §6) is sourced from the Kyte-tier write-up cited in file 04, now reinforced by a live-verified real buff type (`NiceBuffType.upStarweight`, found on Okita Souji's skill 2) for the "Star Focus" multiplier — see file 04 §6.2/§6.3 for full detail.

## 7. Open items carried into implementation (not blocking design, but should be tracked)

- **Card-draw weighting/guarantee rule** (§3): no primary or Kyte-tier source found (this session or prior) for exactly how the 5-of-15 non-NP card draw is weighted — flagged as the largest remaining gap for exact (not Monte-Carlo-approximated) chain-probability math. Recommend a targeted search pass specifically for this before the probability-of-clear feature ships, rather than shipping an assumed-uniform draw model silently.
- ~~Star carryover-to-next-turn cap~~ — **resolved (file 04 §6.3, follow-up pass): not a real mechanic.** Stars don't accumulate past one turn — a turn's generated stars are allocated to the *next* turn's crit chances via the weighted lottery (file 04 §6.2) and anything unspent is simply discarded, not banked for a further turn. `NiceConstant.STAR_RATE_MAX = 3000` remains a separate, unrelated per-hit generation-rate ceiling. No cap constant is needed in the engine; `BattleState.starsCarried` (§1) only ever needs to hold one turn's worth of stars.
- **Order Change state-transfer verification** (file 07 §4): still wiki-tier only. Given the farming-optimizer's Order Change loop modeling depends on it, this should be the first thing verified via a live battle-log trace if/when Order Change loops become a concrete feature, rather than shipped on wiki-tier trust alone.
- **Evaded/Invincible-blocked hit's gauge/star yield** (file 00 §4, restated in §2 above): still open after files 01/04/05/08 — no source found. The engine should make this a configurable flag per buff type (default: no gauge/star from Evade since the hit never connects; some gauge/star from Invincible since the hit connects but deals 0 damage — this default guess is consistent with Invincible vs. Evade's known mechanical difference, file 00 §4, but is an inference, not a sourced fact) and flag it in the UI as an assumption, not silently bake it in.
- **"Current event" detection heuristic** (file 00 §1.1 "Prefer Event CE" — the curated-list/ID-scan mechanism file 01 flagged as an implementation detail for this file): concretely, maintain a small app-side table `{eventId → startDate/endDate}` populated by periodically scanning new CE `funcGroup.eventId` values against JP's event calendar (no dedicated "active now" endpoint exists, confirmed by file 01) — this is an ops/maintenance task, not a research gap, and manual override (file 00 §1.1) remains the safety net for staleness.
- **Gap-analysis upgrade-ranking heuristic** (file 00 §4, §1.4): recommend ranking candidate upgrades by a simple **effort proxy** (skill-level-up < NP-level-up < Interlude-unlock < new-servant-acquisition, in that rough order) combined with **margin-closed-per-upgrade** (how much of the damage/turn-count gap a given upgrade closes) — e.g. prefer the smallest-effort upgrade that closes the gap, only recommending a larger-effort upgrade if no smaller one suffices. This is a design recommendation, not something sourceable from Atlas Academy data — flagged as a product decision to confirm with the user before implementation, not a citation gap.
- **`criticalRate`/`recover` (enemy-side crit/recovery stat) numeric formulas** (file 08 §5) — remains untraced; not required for the damage-output-only scope (file 00 §2), only relevant if/when enemy-attack simulation (phase 2) is built.
