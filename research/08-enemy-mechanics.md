# 08 — Enemy Mechanics: Rank/Server-Mod, Traits/Resistances, Wave/HP Structure, Break Bars

This file resolves the four items on file 00's roadmap line for file 08: the "enemy rank (Bronze/Silver/Gold)" question specifically flagged by the user as not-to-be-missed, enemy traits/resistances, wave/HP structure, and gauge-break bars. It also closes out remaining open questions from §6 of `00-project-overview.md` regarding enemy-side NP/debuff mechanics.

Sources: the Atlas Academy OpenAPI schema (`QuestEnemy`, `EnemyScript`, `EnemyServerMod`, `EnemyAi`, `EnemyMisc`, `BuffScript`/`Vals` resistance fields — primary), live quest-phase data fetched this session (`/nice/JP/quest/{id}/{phase}`), and `fgo-docs`' `np.md`/misc-notes (already cited in files 02/04/05).

## 1. "Enemy rank (Bronze/Silver/Gold)" — not an official Atlas Academy or `fgo-docs` concept; the real mechanism is `EnemyServerMod`

This was explicitly flagged by the user in file 00 §6 as a mechanic not to miss. After searching the full OpenAPI schema for "bronze"/"silver"/"gold" and the credible community sources (`fgo-docs`, Kyte's NP-gain post), **no such 3-tier "enemy rank" terminology or mechanic exists in any primary or Kyte-tier source** — the only schema hits for those three words are `NiceItemBGType` (`zero/bronze/silver/gold/...`), which is purely the **material drop-item icon background color** (a UI/rarity-display concept for items, unrelated to enemies or NP gain).

**Follow-up pass — mostly resolved, community-cross-tier**: the project owner recalled that enemies genuinely do have a Bronze/Silver/Gold rank, prompting a further search that confirmed it as a real, systematic in-game concept (cross-corroborated across Fandom Wiki, GamePress, and Samurai Gamers):

- It's a literal UI label: the battle screen's enemy info panel shows "name, class & rank (gold/silver/bronze), level, HP" for every non-servant enemy (Fandom Wiki, `Battle` page) — separate from the class icon, and distinct from the `NiceItemBGType` material-icon concept ruled out above.
- **It correlates with rarity** (mirroring the servant star-rarity convention: low-rarity mobs are bronze, mid silver, high gold) — GamePress's own enemy database catalogs generic mob variants literally as e.g. "Helter Skelter - Bronze Archer" vs. "Helter Skelter - Gold Archer" as separate entries, confirming this is a systematic classification, not colloquial slang.
- **Mechanically, it primarily governs actions-per-turn, not a damage/NP-gain formula term**: per GamePress's "Assessing the Enemy" guide, Gold-rank enemies act ~3 times per turn (Gold Berserkers act twice), Silver ~2 times, Bronze 1–2 times. This is a real combat-relevant mechanic, but only matters for **enemy-attack simulation** (out of this project's current damage-output-only scope, file 00 §2) — it does not feed into the player-damage-output formulas this project models.
- **Loot correlation**: skill-gem tier drops correlate with rank (Samurai Gamers) — "Gem" from Bronze/Silver, "Magic Gem" from Silver/Gold, "Secret Gem" from Gold only.

**Still unresolved**: no source found gives an exact rarity→rank threshold table (e.g. "1–2★ = Bronze"), and no Atlas Academy schema field was confirmed to encode this rank directly (plausibly a `rarity`-adjacent field on `NiceEnemy`/`QuestEnemy`, distinct from `EnemyServerMod`, but not checked this pass). Flagged **open, low priority** — out of scope unless/until enemy-attack simulation (phase 2) is built, at which point the actions-per-turn mechanic would need this resolved.

**What *is* confirmed, and is very likely what the underlying concern was actually about**: `EnemyServerMod` (`QuestEnemy.serverMod`) is a real, per-enemy, per-quest, server-supplied set of three per-mille multipliers:
- `tdRate` — the `enemyServerMod` term in the **attacking** NP-gain formula (file 04's `np.md` citation)
- `tdAttackRate` — the `enemyServerMod` term in the **defending** NP-gain formula
- `starRate` — the `serverRate` term in the crit-star-generation formula (`critstars.md`)

Live-verified this session (`quest/1000001/1`, `quest/94061636/1`): ordinary early-game mobs (Skeletons, and Treasure Vault (宝物庫) "Door" enemies at `lv:10` in quest 94061636 — previously mislabeled a training quest) all show `{tdRate: 1200, tdAttackRate: 1200, starRate: 0}`. **Corrected 2026-11-06**: `starRate` is an *added* term in the star-drop formula (fgo-docs `critstars.md`, `+ serverRate`), so `starRate: 0` means **no adjustment**, not 0% star generation. And `tdRate: 1200` is not evidence of a "deliberately boosted" quest: the Door enemies are Caster class, which normally carries 1200; other sampled quests follow class values (e.g. 93000101/3: lancer `1000/1000/-50`, saber `1000/1000/0`). The Fuyuki skeletons (saber, 1200) do look like a genuine exception. A `danger`-role enemy in the same quest (`勇者の扉`, higher HP, higher level) showed the **identical** `serverMod` values as the `normal`-role enemies in the same wave — **`EnemyRoleType` (`normal`/`danger`/`servant`) does not by itself determine `serverMod`**; the two are independently set per enemy record by quest design, not derived from a rank tier. **Practical modeling consequence**: the engine must read `serverMod` directly per enemy from live quest data (it mostly follows the enemy's class but varies by enemy record) — it must not hardcode a 3-tier "Bronze/Silver/Gold" table, because no such fixed table exists in the data.

## 2. Enemy traits and resistances

**Traits**: `QuestEnemy.traits` is a plain `NiceTrait[]` list — the exact same closed 375-value enum documented in file 06, no enemy-specific extension. Enemies get their trait-gated interactions (e.g. "extra damage vs. Undead," Ruler-class NP effects that check `ckOpIndv`) through this identical mechanism — no separate enemy trait taxonomy exists.

**Resistance to debuffs/instant-death** (refining file 05 §4's MISS/GUARD model with the exact toggle fields found this session): the debuff-application function's `BuffScript`/`Vals` object carries **`UseSvtResistRate`** and **`UseBuffResistRate`** — independent boolean flags controlling whether the "target's resistance" term in the `num2 = resistance + random_roll` formula (file 05 §4) should include (a) the target's own innate/base resistance stat and/or (b) any resistance-type buffs currently on the target. A separate **`IgnoreResistance`** flag lets a specific function bypass the resistance check entirely (a guaranteed-apply debuff, regardless of the target's stats/buffs). This means "an enemy is immune to Stun" is not a hardcoded special-case in the engine — it's the general resistance formula with a resistance value high enough (via base stat and/or buff) that no roll can beat it, exactly the same mechanism used for player-side debuff resistance.

**Instant death** is its own `funcType: instantDeath` (confirmed in the `NiceFuncType` enum), resolved against a base **`instantDeathChance`** field present on `NiceServant` (and the enemy-record equivalent `QuestEnemy.deathRate`) — both per-mille "susceptibility" values, not a flat immunity flag. A `upResistInstantdeath`/`upNonresistInstantdeath` buff-type pair exists (confirmed in `NiceBuffType`), meaning instant-death resistance stacks the same additive way as any other numeric buff (file 05 §2) on top of the base `deathRate`/`instantDeathChance` value — a boss with `deathRate: 0` would be a hard, stat-level immunity (common for story-relevant/named enemies) rather than needing a scripted flag. `NiceConstant.USE_NEW_LOGIC_PREVENT_INVISIBLE_WHEN_INSTANT_DEATH` (confirmed present, value `1`) hints at a client-side visual-only interaction between instant-death and invincibility with no further detail found — flagged open, likely out of scope for damage-only modeling. **Implemented 2026-09-08, in two passes.** First pass folded in `resistInstantdeath` alone. **Second pass, same day — the full formula, community-sourced (firq.dev's "Instant Death Success Rate" article, cross-referenced against live `funcTargetType` data for each buff type — this tier, not project-owner live-tested):**

```
finalChance = hitRate * (enemy.deathRate / 1000) * (1 + grant - resist + nonresist)
```

- `hitRate` = the skill/NP's own `InstantDeathEffect.deathRate` (unchanged).
- `enemy.deathRate` = **new**, `EnemyInstance.deathRate` (`src/battle/battleState.ts`) — this enemy's own `QuestEnemy.deathRate`. No `WaveEnemy`-construction pipeline exists yet to source this automatically (same standing caveat as `npTurnLimit`); firq.dev cites typical values by rarity (Bronze 80%, Silver 50%, Gold 20%) for a caller building one by hand.
- `grant` = `grantInstantdeath` (`upGrantInstantdeath`/`downGrantInstantdeath`) — **attacker-side**, confirmed by live data: every example is `self`-targeted (e.g. Nitocris' skill 1, firq.dev's own cited example).
- `resist`/`nonresist` = `resistInstantdeath`/`nonresistInstantdeath` — **both target-side**, despite "nonresist" reading like an attacker-side "ignore resistance" buff: live data shows `resistInstantdeath` is `self`/`ptAll`-targeted (an ally buffing their own resistance, e.g. Taira no Kagekiyo's skill 2) while `nonresistInstantdeath` is `enemy`/`enemyAll`-targeted (a debuff lowering the target's effective resistance, e.g. Void Shiki's skill 1) — both firq.dev's own cited examples, confirming the live-data cross-reference against the community formula.

`applyInstantDeathEffect` now implements this in full, clamped to `[0, 1]` before rolling, and routes a success through `resolveGuts` (see file 09 §7 for the Guts-interaction finding — cross-corroborated community sources, not this session's formula source).

**Other per-enemy "Luck/Magic/Agility rank"-flavored stats**: `criticalRate` and `recover` are additional plain integer fields on `QuestEnemy` (alongside `deathRate`) — Kyte's NP-gain-era community notes (cross-referenced against the cached forum thread this session) describe `criticalRate` as tied to the enemy's effective Luck parameter and `deathRate` to Magic, consistent with these being real, direct numeric knobs per enemy record rather than derived from class/rank. No live numeric-effect formula for these two (beyond the schema field names themselves) was pinned down this session — flagged open, lower priority since neither the current damage-only scope nor near-term farming-optimizer work depends on modeling enemy crit/instant-death behavior *against* the player.

**"Card Performance Resistance" — a new, real gimmick mechanic identified this pass (project owner's recollection, community-tier confirmation)**: some quest-specific enemies carry a per-card-type damage (and NP-gain/star-generation) resistance, up to and including full immunity to one specific card type — this is genuinely different from `NotPierceIndividuality`/Invincible-piercing (file 05 §5, which is trait-based and about bypassing a defender's Invincible/Evade buff entirely, not card-type-specific). Clearest example (GamePress): **Battle in New York 2021, Exhibition 3 — "The Three Beautiful Gorgon Sisters"** — each of the three sisters has 100% Card Performance Resistance matching her own NP's card type (Euryale: Arts-immune, Stheno: Buster-immune, Medusa: Quick-immune), meaningfully damageable only by the *other two* card types; GamePress explicitly notes this resistance also reduces NP gain and star generation from the resisted card type, not just damage. A softer example: **Lostbelt 7 chapter 10-2's Archer enemy**, with 80% resistance to both Arts and Quick, making Buster the practical way to damage it. **Source tier: community only (GamePress)** — no primary schema field was identified for the underlying mechanism this pass; a quick check of `NiceBuffType` found no obviously-named "card resist" enum value, and these are event-exclusive enemy NPCs not exposed via the standard servant-search endpoint, so the live buff/function record wasn't traced. Most likely implementation, by analogy with existing project research: a per-enemy `damageRate`-reducing function conditioned on the attacking card's type via a card-type trait gate (similar to the `ckOpIndv` machinery documented in file 05 §4), but this is inference, not confirmed. Flagged **open** — worth a targeted API pull against a known quest ID hosting one of these enemies (e.g. the Gorgon Sisters exhibition) if/when this mechanic becomes load-bearing for enemy-config modeling.

## 3. Wave/HP structure — reconfirms and closes prior findings, no new data model needed

This item was already substantially resolved by `01-data-sources.md` (see `00-project-overview.md` §4's "Multi-bar/segmented enemy HP" and "Enemy reinforcement/spawn-on-death" entries): a wave is a flat list of independent `QuestEnemy` records; multi-bar bosses and reinforcements are both just "one enemy record replaced/joined by another," not a bespoke nested structure. This session's live quest pulls (`1000001`, `94061636`) reconfirm the flat-list shape in practice — a 3-wave quest is simply 3 separate `stages[].enemies[]` arrays, each entry a fully self-contained `QuestEnemy` (own HP/level/traits/serverMod/skills/AI), matching the "wave = list of independent enemy unit records" decision already recorded in file 00 §3.

## 4. Gauge-break bars — confirmed to be the exact same mechanism as multi-bar HP, on Atlas Academy's own naming

This closes the file 00 roadmap item cleanly: `EnemyScript.shift` (an array of NPC IDs) is Atlas Academy's own field, and **its schema title is literally `"Break bar switch to these NPC IDs"`** — i.e., what the community calls a boss's "break bar" (or "gauge-break bar") **is not a separate mechanic from the multi-bar/segmented-HP structure already resolved in file 01** — it is the *same* `shift` field, just applied to the specific case of a boss's HP-bar-emptying transition (as opposed to `call`, which is "summon a new/additional NPC," a materially different trigger already distinguished in file 00 §4). No live example enemy record with a populated `shift` array was captured this session (would require locating a specific multi-bar raid/CQ quest ID, not attempted here) — the mechanism is schema-confirmed via the field's own official title text, consistent with this project's standard of treating Atlas Academy's own schema descriptions as primary-source-equivalent (same treatment given to `NiceBuff.vals`' dispel-target description in file 05). Flagged as a live-example gap, not a mechanism gap.

**Practical consequence, reconfirmed**: no bespoke "break bar" data structure is needed in the engine beyond what file 01/00 already decided — `shift` and `call` are the two enemy-transition triggers or bars/reinforcements are keyed off (HP-empty vs. death/turn/threshold respectively), and both resolve to "swap in this other already-present enemy record."

**`shift` implemented, 2026-09-08 — `call` deliberately deferred.** Two new pieces: `buildEnemyInstance` (`src/battle/battleState.ts`) is the `WaveEnemy`→`EnemyInstance` constructor this project didn't have yet (every field this session added — `currentNpTurns`/`npTurnLimit`/`deathRate`/`readyToNp` — had been noting "no construction pipeline exists yet" as a standing caveat; this closes that for all of them at once). `applyShiftTransitions` (`src/battle/turnLoop.ts`) scans `state.enemies` for `currentHp <= 0` after every hit/instant-death resolution, looks up the dead enemy's static `WaveEnemy` record in `state.waves[state.currentWaveIndex].enemyPool`, and — if `resolveShiftTargets` (`src/quest/types.ts`) resolves a target — rebuilds it into a fresh `EnemyInstance` that takes over the same array slot, exactly the "HP hit 0, has a `shift` target → swap in the next record instead of dying" event research/00/01 already specified. No target found (missing `shift`, or the referenced npcId isn't in this wave's pool) leaves the entry genuinely dead, unchanged from before this pass.

`call` (reinforcement) is intentionally NOT wired this pass — unlike `shift`'s unambiguous "HP hits 0" trigger, no research pass (this project's own or the cited primary sources) pins down `call`'s exact firing condition: death of the specific enemy carrying it? a turn count? another enemy's death? Modeling it now would mean guessing at a trigger, which this project's sourcing standard doesn't allow. Flagged as the next concrete open item if wave/death transitions are revisited.

**Also flagged, not silently assumed**: `shift`'s array can list more than one npcId, and no schema note or live example in this project's research says what a multi-entry array means (simultaneous multi-target transition? an ordered fallback list?) — `applyShiftTransitions` takes only the first resolved entry, documented as an open reading rather than a confirmed one.

## 5. Enemy NP gauge is a discrete per-turn counter, not a percentage — structurally different from `ServantInstance.currentNpGauge`

**Confirmed by the project owner's own direct gameplay knowledge (2026-09-08), then live-verified against the schema**: unlike a player servant's gauge (a continuous 0–100%+ value, `FULL_TD_POINT`-unit, driven by the attacking/defending NP-gain formulas — files 02/04), an **enemy's NP gauge is a simple integer countdown**. It advances by exactly **+1 per turn** (barring a skill/gimmick that changes the rate), and once it reaches its own max — a **per-enemy value that varies** (the project owner's own recollection: commonly 4 or 5, but not fixed) — the enemy automatically casts its NP that turn. No formula, no card-type/crit/Overcharge inputs at all: a flat, deterministic tick.

This maps directly onto `QuestEnemy.chargeTurn`, live-confirmed this session (`GET /nice/JP/quest/{id}/{phase}`): every enemy record carries an integer `chargeTurn` field — `5` on a live example (quest `94061636`, several enemy records, each also carrying a `noblePhantasm` block), `0` on non-NP-capable enemy records in another quest (`1000001`) — matching the "varies per enemy, sometimes absent" description exactly. `chargeTurn` reads naturally as the enemy's own max bar count (the countdown target), not the current progress — meaning **the *current* per-enemy NP-turn progress is a live, mutable value this project's `QuestEnemy`/schema pull doesn't expose separately** (it's presumably server-side battle state, not static quest data) — `EnemyInstance` (`src/battle/battleState.ts`) needs its own new field for it (something like `npTurnsRemaining: number`, initialized from `chargeTurn`, ticking down by 1 at `resolveEndTurn`, triggering an enemy NP cast at `0` — mirroring `ServantInstance.currentNpGauge`'s role but with entirely different mechanics, not a percentage reuse).

**Direct practical consequence for the `delayNpturn`/`lossNp`/`hastenNpturn` `FuncType`s (research/09 §7)**: against an *enemy* target, these read cleanly as integer bar-count operations on this same counter — `delayNpturn: Value=N` adds `N` to `npTurnsRemaining` (pushes the countdown back, i.e. "delays" the auto-cast by `N` extra turns), `lossNp` (enemy-targeted, e.g. Tamamo no Mae's "呪術" skill) subtracts from it directly (setting the enemy's bar count back, e.g. -1 bar), and `hastenNpturn` (enemy-targeted, rare — the *player*-side "buff granted alongside `regainNp`" reading, §7's already-resolved finding, is the far more common ally-side case) would symmetrically subtract from `npTurnsRemaining` to speed up an ally's — or in a PvP/quest-scripted context, an enemy's own — auto-cast countdown. This is a structurally *much* simpler mechanic than the player-side gauge-percentage reading these `FuncType`s were previously being evaluated against, and doesn't share `hastenNpturn`'s player-side "needs a `regainNp` buff to have any effect" caveat — an enemy's countdown ticks unconditionally every turn regardless of buffs.

**Initial value confirmed (project owner's gameplay knowledge, 2026-09-08)**: `currentNpTurns` starts at `0` at the start of a battle, unless a specific quest/enemy gimmick says otherwise (e.g. a scripted "this enemy starts with its NP gauge already charged" setup, which would need to be modeled per-quest when the enemy-from-`QuestEnemy` construction path is eventually built — no such construction path exists yet, so this is a note for that future work rather than a code change today).

**Follow-up pass — the countdown state is now built.** `EnemyInstance` (`src/battle/battleState.ts`) gained `currentNpTurns`/`npTurnLimit` (a `currentHp`/`maxHp`-shaped pairing, `npTurnLimit` sourced from `chargeTurn`), and `advanceEnemyForEndTurn` (`src/battle/turnLoop.ts`) advances `currentNpTurns` by exactly `+1` per turn, capped at `npTurnLimit` — unconditional, no formula, matching the mechanism above.

**Trigger flag added, 2026-09-08 — deliberately scoped to "flag only," per the project owner's explicit choice among 3 offered scopes (flag-only / full enemy-attack simulation / detection-only-no-reset).** `EnemyInstance` gained `readyToNp: boolean`. `advanceEnemyForEndTurn` now resets `currentNpTurns` to `0` and sets `readyToNp: true` the moment the countdown reaches `npTurnLimit` (a new cycle starts), instead of capping and sitting there forever. The actual enemy NP effect — damage/buffs/debuffs applied to the servants — is still **not implemented** (unchanged "phase 2, enemy-attack simulation" scope boundary): nothing reads or clears `readyToNp` yet, so a future "resolve the enemy's attack" step is the one responsible for consuming it. A documented simplification versus the real game: once `readyToNp` is set it stays `true` indefinitely if nothing consumes it, even as `currentNpTurns` keeps cycling underneath — the real game's enemy reliably casts on its very next turn once ready rather than potentially sitting "ready" for several turns. `npTurnLimit <= 0` (a non-NP-capable enemy) is guarded explicitly so it never becomes `readyToNp: true`. `delayNpturn`'s enemy-targeted majority is now modeled too, as `DelayNpTurnEffect` (`src/battle/skillEffect.ts`) — its raw `Value` reads directly as a turn count with no unit conversion needed (unlike `gainNp`'s per-mille convention), subtracted straight from `currentNpTurns`, floored at `0`. **Resolved by live testing, 2026-09-08**: enemy-targeted `lossNp` (the far more common companion `FuncType`, 37 of 50 live `lossNp` instances) is a confirmed no-op, not an unconfirmed guess. The project owner tested Tamamo Cat's "呪術 E" skill and Waver/Zhuge Liang's NP (both the standard `delayNpturn: 1` + `lossNp: 2000` pairing) and both moved the enemy's NP bar by exactly 1 pip — fully explained by `delayNpturn` alone, nothing left for `lossNp` to contribute. Stays unmodeled, but now because there's nothing to model, not because the ratio is unverified. The mirror case — self/`ptOne`-targeted `delayNpturn` against a *servant* — resolved the opposite way in the same testing pass: `lossNp` turned out to be the real mechanism there (a flat `FULL_TD_POINT`-scale subtraction, already correctly modeled by the existing `LossNpEffect`) and `delayNpturn` is the no-op, exactly mirroring how `hastenNpturn` resolved (§7 below, and `src/battle/skillEffect.ts`'s `LossNpEffect`/`DelayNpTurnEffect` doc comments carry the full measurements).
