# FGO Damage Calculator & 3-Turn Farm Optimizer — Project Overview

This document is the master reference for the project. It captures the goal, scope, decisions made so far, and the research/build roadmap. It is written **before** any detailed mechanic research so that all later research stays anchored to the same target. No web research was performed to produce this file — it reflects the requirements gathered from the user plus general domain framing. Every claim about actual FGO formulas/numbers will be sourced and cited in the topic-specific research files listed below, not here.

## 1. Goal

**Who this is for**: two audiences, same engine — (a) newer/low-roster players who are stuck against content that feels "too hard" but is often actually solvable with what they already own, just not built/played optimally; and (b) experienced players optimizing 3-turn clears for 90++ (Lv.90+ difficulty) events and Challenge Quests (CQ), where the margins are tight and exact skill/card ordering matters a lot. The tool should serve both: "can I clear this at all, and how" for the first group, "what's the fastest/most reliable 3T line" for the second.

Build a comprehensive, data-driven FGO (Fate/Grand Order) damage & NP calculator, evolving into a **fastest-clear farming optimizer** (3T is the flagship/most common target, not a hardcoded limit) and a **strongest single-target (ST) burst finder**.

**Generalized wave/turn scope**: the engine is designed for **any number of waves (N)**, searching for the **minimum turn count (M)** to clear — 3-wave/3-turn is simply the most common target (M target = 3), not a hardcoded assumption. This lets the same engine handle a 1-wave daily quest, a standard 3-wave farming node, or a 4+ wave Challenge Quest without special-casing wave count anywhere in the design.

Two end-user outcomes:

1. **3T Farm Optimizer** — Given an enemy composition (3 waves, each wave's enemy count/class/attribute/HP/rank), and the user's owned roster (+ optionally a "preferred servant" the user wants included, or "let the system suggest"), recommend:
   - Which servants to bring (up to 6, but the system should stop adding servants once a lineup can already clear reliably — "auto-degenerate" to the minimal sufficient team).
   - **Core vs free-slot tagging**: every recommended lineup must explicitly mark which servants are **core** (actually required to execute the clear — e.g. the 3 that make up the Arts/Buster loop) vs which remaining slots are **free/flexible** (padding servants where the user can put literally anything, since they contribute nothing to the actual clear plan). E.g. for a 3-servant loop, those 3 are tagged core and the other 3 party slots are explicitly labeled "free — bring whatever you want" rather than left ambiguous.
   - **Total Cost reporting**: every recommended lineup's result must include its **total party Cost** (sum of the core servants' + their CEs' Cost — see Master-level Cost budget below) alongside the damage/turn-count/probability info, so the user can immediately see affordability without cross-checking manually. Free/flexible slots' Cost should also be reported once the user actually fills them, or shown as "remaining Cost budget available for free slots."
   - **"Minimum Cost" optimizer preference**: an alternative ranking/search mode — instead of optimizing purely for highest clear-probability or safest margin, prefer the **cheapest viable lineup** (lowest total Cost among lines that still clear reliably). Useful for lower Master-level accounts or when the user wants to preserve Cost budget for other purposes. This is a distinct sort/objective from the default ranking, not a replacement for it — the UI should let the user pick which objective drives the Top-5 results (best probability/turn count vs cheapest Cost vs, per below, best event-CE coverage).
   - **"Prefer Event CE" mode** (for event-material farming): analogous to "Prefer Bond CE" — bias CE selection toward the current event's drop-rate-up CE(s) on as many party slots as possible without breaking the clear, with the same soft/per-slot fallback (a slot that needs an offensive/charge CE to remain viable keeps it). Report total effective drop-rate-up% for the lineup the same way Bond mode reports total Bond Point %, since stacking multiple event CEs' drop%-up is the actual goal of this mode. **Resolved by file 01 research**: auto-detection is buildable, not a manual-only fallback. A CE's event-drop function (`funcType` = `eventDropUp`/`eventDropRateUp`) carries a `funcGroup.eventId` field that directly names which event it boosts — so the app can scan the user's owned CEs for this field and match it against whichever event is currently active. The one remaining wrinkle: Atlas Academy has no single "what event is active right now" endpoint (no search-by-date), so "current event ID" needs to come from a small curated list or an ID-scan job the app maintains — an implementation detail for file 09, not a data-availability blocker. **Manual override should still exist** as a safety net (e.g. if the app's "current event" detection is stale or wrong), but it's a fallback, not the primary path.
   - Which support servant(s) to borrow from friend/rental list (if applicable).
   - Per wave: which skills to use (in what order, on whom), which servant attacks, whether they NP, whether they Order Change, and why.
   - Estimated damage, **NP gauge gain / NP refund** (per hit, per card, and the resulting total gauge % after each action), and overkill status per hit/card/NP, wave by wave, until all waves are cleared — ideally within the user's target turn count (commonly 3, but configurable/any N per the generalized scope above), reporting the actual minimum achievable turn count when the target isn't reachable. Results must surface both the fine-grained per-hit/per-card breakdown **and** a rolled-up **per-wave summary** (total damage dealt in that wave, whether it was enough to clear the wave's enemies, resulting NP gauge per servant entering the next wave) so the user can sanity-check at whichever level of detail they want.
   - Compare multiple viable strategies (Arts loop vs Buster loop vs ST alpha-strike opener vs mixed) and rank by probability of successful clear within the target turn count (accounting for card RNG where relevant) and/or by turn count / safety margin.
   - **Preferred servant / preferred attacker constraint**: the user can optionally pin a single servant as the **preferred main attacker** (role, not just "include somewhere in party") — the optimizer must then search specifically for lines where that servant is the primary damage dealer, not merely present in the party. Full auto (no preference) remains the default/baseline mode.
   - **Top-N results, not just one answer**: the optimizer returns **up to 5** distinct highest-probability/best-ranked combinations (different servant/support/skill-order lines), so the user can compare trade-offs rather than getting a single "the" answer.
   - **Fallback suggestion when the preferred attacker doesn't work**: if no viable line achieves the goal (3T, or clear at all) with the preferred attacker in the main-attacker role, but a different combination *without* them does succeed, the optimizer must still surface that alternative explicitly (clearly labeled as "not using your preferred servant, but this works") rather than only reporting failure.
   - **"Prefer Bond CE" mode** (for bond-point farming): a toggle that biases CE selection toward Bond CEs (the free, un-upgradeable CEs earned from reaching bond level with a servant, most of which grant a "Bond Point Up %" effect) as much as possible without breaking the clear. Behavior: try to equip Bond CEs on **every** party slot first; if a specific slot's role genuinely requires a non-Bond CE to remain viable (e.g. the main attacker needs an offensive NP-damage CE like Black Grail to reach lethal, or a support needs an NP-charge CE to deliver enough Overcharge), allow that slot to keep its non-Bond CE while the rest still use Bond CEs — i.e. this is a **soft/partial preference with per-slot fallback**, not an all-or-nothing switch. When this mode is on, the optimizer should also **compute and report total effective Bond Point gain** for the recommended lineup (see Bond Point calculation below), not just "how many Bond CEs got equipped" — since that's the actual metric a bond-farming user cares about, and different Bond CEs have different %Up values.
   - **Bond Point calculation as an optimizer objective**: total bond point gain per clear = base bond points from the quest × (1 + sum of all active "Bond Point Up %" sources). Two distinct sources stack into that sum and must both be tracked: (a) each equipped Bond CE's own %Up value (varies per CE, and may itself differ if MLB — needs sourcing), and (b) a **flat +25% party-wide bonus that triggers if any fielded servant (front-line or sub-member — needs confirming which) has reached Bond Level 15**, independent of what CE that servant is wearing. This means a party can benefit from the Bond-15 bonus even on slots that aren't using a Bond CE at all, so "prefer Bond CE" mode and "does anyone in the party already have Bond 15" are two separate, additive levers the optimizer should account for — including suggesting "field this Bond-15 servant even in a support/sub role just for the +25%," if that doesn't compromise the clear.

2. **Strongest ST Burst Finder** — Given a boss's stats (HP, defense, class, attribute, traits, resistances), find the highest-damage single-target burst achievable from the owned roster (e.g., for oneshotting a high-DEF/high-HP boss), including buff-stacking chains across multiple support servants feeding one attacker.

3. **Manual/Sandbox Builder** — Independent of the auto-optimizer: let the user freely construct their *own* turn-by-turn plan (pick servants, skill usage/targets/order, card selection, NP casts, Order Changes, mystic code usage) for any scenario — 3T farm, ST burst, or anything else — and have the engine **simulate and report the outcome** (damage per hit/card/NP, NP gauge trajectory, overkill, whether/when enemies die, final turn count) without the system auto-searching or suggesting anything. This reuses the exact same simulation core as the optimizer (§1.1/§1.2), just driven by user choices instead of a search algorithm — so the user can hand-craft and verify their own strategy, then optionally ask the optimizer to suggest improvements or alternatives on top of it.

4. **"Not Clearable Yet" Gap Analysis / Build-Up Advisor** — When no combination from the user's *current* roster state can clear the given content, don't just say "not possible." Instead: (a) identify the closest-to-working line(s) the optimizer found, (b) run a sensitivity/what-if simulation that incrementally idealizes specific inputs (e.g. "+1 skill level on Skill 2," "NP1→NP2," "+10 Fou ATK," "unlock this Interlude," "MLB this CE," "append skill X unlocked") to find the **smallest concrete upgrade(s)** that would flip the result from "fails" to "clears," and (c) report that as an actionable to-do list ("if you level Skill 3 of Servant X to 10 and MLB CE Y, this line clears"). This is essentially the optimizer run twice — once against the real account state, once in a "what would need to change" search mode — surfaced as a diff between the two.

5. **Multi-Turn Setup Strategies (not just single-turn burst)** — The ST/burst finder must support plans that spend one or more turns on **setup** before the actual kill turn — e.g. Turn 1: apply buffs/charge NP/no kill yet; deliberately focus damage on a *specific* lower-priority enemy so it dies first (because its death triggers something relevant — a reinforcement/support enemy appearing, an ally Order Change opportunity, or simply clearing a body blocking a better target); Turn 2+: bring in the real attacker/support chain and execute the burst. This means the engine must model **multi-turn planning as a first-class case** for the burst-finder too, not just "maximize single-turn damage" — including tracking mid-fight state changes like new enemies spawning after a specific enemy's death (common in CQ/event boss mechanics) and Order Change timing relative to that. This category also covers the count-based Evade/Invincible "bait-then-burst" pattern described under Evade vs Invincible in §4 — deliberately spending sacrifice attacks first to burn down a defensive buff's count before landing the real NP is the same kind of setup-then-execute planning, just within a turn rather than across turns.

## 2. Non-goals (for now)

- **Enemy attack/survivability simulation — data is available, but staying damage-output-only for the initial build (deliberate phasing, not a data limitation).** `01-data-sources.md` confirmed Atlas Academy **does** expose enough enemy-side data to simulate this properly: enemy NP/skill definitions (full `NiceSkill`/`NiceTd` objects, same as player servants), an AI action-priority/target system (`EnemyAi`/`NiceAiAct`), deck composition, and attack stats (`atk`, card/NP data). So the earlier "if no data, stay damage-only" framing is moot — the real reason to defer this is that the AI system is priority/weight-based rather than a flat deterministic script, so building an *accurate* enemy-turn simulator is a nontrivial modeling effort on top of having the raw data. **Decision: ship the damage-output-only engine first; treat full enemy-attack/survivability simulation as an in-scope phase-2 feature**, not a maybe. As before: don't build the damage-only version so rigidly that adding survivability later requires a rewrite (the underlying enemy skill/NP/AI data will already be flowing through the same engine once file 08/09 are built).
- Not modeling gacha/rolling, servant leveling investment cost, or in-game currency.
- Not a mobile/native app — web app only.
- Not attempting to hardcode data for every servant/CE/enemy by hand — see Data Strategy below.

## 3. Key Decisions (already made)

| Decision | Choice | Rationale |
|---|---|---|
| **Data source** | [Atlas Academy API](https://api.atlasacademy.io) (`nice` data format) as source of truth for servant/skill/NP/CE/mystic code/enemy data | Thousands of servants/CEs, constantly updated by game patches — hand-writing this data is infeasible and would rot immediately. The app fetches structured JSON at runtime/build time instead. |
| **Region is a user-switchable setting, with fully separate stored account data per region** | The app supports multiple game regions via Atlas Academy's per-region endpoints (e.g. `/nice/JP/...` vs `/nice/NA/...`). Switching the active region **swaps which stored account profile is in use** — it does not merge or overwrite data. A user who plays both a JP and an NA account keeps **two independent roster datasets** (separate servant ownership/levels/skills/CEs/etc. per region), and switching the region setting just changes which one the app currently reads/writes | JP is consistently ahead of NA/EN in content (newer servants/CEs, Rank-Ups/Interludes land there first), so a JP-only or NA-only assumption would misrepresent one group of users' real account state. Since a JP account and an NA account are genuinely different accounts with different real progress, the data storage layer must key everything (servant roster, CE inventory, Mystic Codes, saved support presets, Master level/Cost) by region — not just tag a single shared roster with "current region," which would corrupt data the moment someone actually maintains two accounts. |
| **Research scope** | Focus on the **generic calculation engine**: formulas and mechanics that apply to *any* servant/skill/buff, not a hand-curated catalog of every unique servant mechanic | Keeps research finite and maintainable. Servant-specific quirks (e.g. Bazett's unique NP-charge-from-damage-taken, Space Ishtar's Arts-chain synergy) are documented only as **illustrative edge cases** of a general rule (e.g. "a function can trigger off `takeDamage` event," "a buff can special-grant NP per Arts card in a chain"), so the engine can represent them generically via the same function/buff data structures Atlas Academy already exposes — not as one-off special-cased code. |
| **Optimizer approach** | Turn-by-turn **simulation + search**: simulate actual damage/NP gain card-by-card from real servant data, then search (brute-force for small spaces, heuristic/pruned search for large ones) over party composition × skill usage × card selection to find viable/optimal 3T lines | More accurate and general than a rule-based "pattern matcher" against known community strategies (Arts loop, Buster loop, etc.); those known strategies should *emerge* from the simulation+search rather than be hardcoded as the only options, though they're useful as heuristics to prune the search space. |
| **Docs language** | English | Matches FGO community terminology and Atlas Academy's own docs/field names, easier to cross-reference sources. |
| **Account data** | Stored locally (manual entry): servant list w/ level, skill levels, **NP level (independently 1–5 per servant — not defaulted to NP1)**, Ascension/append skills, Fou values, bond level, equipped CE + CE level/limit break, Mystic Code + level | User's personal roster is not public data — must be entered manually per user, but structure should mirror Atlas Academy's servant schema so it's easy to merge "static" (Atlas Academy) data with "owned" (user) data at runtime. Bond level is needed specifically for the Bond-15 party-wide bonus (see Bond Point calculation). NP level directly changes the NP damage-multiplier `svals` entry read (same "actual account state" principle as skill levels) — must never be assumed uniform across the roster. |
| **CE inventory supports multiple copies of the same CE** | The account's CE collection is a **list of owned copies**, not a "do I own CE X: yes/no" set — the user can own several copies of the same CE (e.g. multiple Kaleidoscopes, multiple Bond CEs of the same servant is impossible but multiple generic-farm CEs like a duplicated welfare CE is common), each copy independently tracked with its own level and MLB/limit-break state. The party-builder must allow equipping more than one copy of the same CE across different servants in one lineup **only up to how many copies the user actually owns**, and never assume infinite copies. | Reflects real FGO CE mechanics — non-story/non-costume CEs are regular gacha/exchange items and duplicates are normal and often desirable (e.g. running the same offensive CE on two different attackers). Ignoring per-copy ownership would let the optimizer suggest impossible lineups (e.g. "equip Black Grail on 3 different servants" when the user only owns one). |
| **Stats at actual level** | Servant ATK/HP, CE ATK/HP, **and every skill's/append skill's effect values (`svals`)** must be computed/read at the user's **actual entered level** for each — servant level+ascension, CE level, and independently **each of the 3 skills' own 1–10 level and each equipped append skill's own 1–10 level** — never assumed at max | Atlas Academy exposes per-level growth curves/per-skill-level `svals` arrays; a servant at Lv.80 with Skill 2 at level 6 (not maxed) hits very differently from the same servant fully maxed, and the calculator must reflect the user's real, possibly-unfinished roster — not a hypothetical fully-invested one. This is the same "pure real account state" principle already applied to Rank-Up/Interlude toggles, extended to every level-dependent number in the kit. |
| **CE Limit Break (MLB) state** | Every equipped CE has an explicit MLB (Max Limit Broken) flag the user sets per copy | Many CEs have two effect-value tiers — base (0 LB) vs MLB — for the same skill (e.g. "NP Damage +30%/40%" style CEs). Must not assume MLB by default; must not assume non-MLB either. |
| **Advanced mode** | Provide an "advanced mode" where the user can override/hand-set individual computed multipliers directly (e.g. force a specific ATK%, NP damage%, class correction, defense%, etc.) instead of only deriving them from selected skills/CEs/buffs | Lets power users sanity-check the engine against known values, model buffs/mechanics the data model doesn't yet cover, or do "what-if" tuning without needing a skill/CE to exist for it. Should layer *on top of* the normal computed pipeline (override specific terms) rather than replace it wholesale. |
| **Per-enemy class/trait/defense/buff state, with data-driven defaults + manual override** | Each enemy has its own class, attribute, trait list, and base defense%, all **pre-filled from a default derived from real quest/enemy data** (e.g. typical raid-boss defense%, class-based baseline) but **individually editable by the user per enemy** — including manually adding buffs/debuffs (e.g. a DEF-up the enemy self-applies) or overriding the defense% multiplier outright | A wave with 3 enemies can have one enemy with a self-buffed DEF-up while the other two are unbuffed — common in FGO (enemy skills, event-specific enemy buffs). The enemy data model must be a list of individual enemy units per wave, each independently configurable, not a single wave-level aggregate — but should still default to sensible data-backed values so the user isn't forced to fill in everything from scratch for a normal fight. |
| **Manual/sandbox mode is first-class, not optional add-on** | The simulation core is usable standalone — driven entirely by the user's own turn/skill/card choices — without requiring the auto-optimizer to run at all | The user explicitly wants to hand-build their own 3T/ST/other strategy and just see it simulated/verified, not only receive system-generated suggestions. UI/architecture must support both "let the system find a strategy" and "let me build one and show me the result" as equally valid entry points into the same engine. |
| **Support/rental servants get full manual entry** | Support servants are configured with the exact same level of detail as owned servants (level, skill levels, NP level, equipped CE + level + MLB, Fou) — no "assumed meta build" shortcut | A friend's actual support build varies a lot and materially changes the calculation; defaulting to an assumed build would produce inaccurate results. The account data model should let the user save reusable "support presets" (e.g. "my go-to Merlin support") to avoid re-entering the same support repeatedly. |
| **Command Seals are modeled, but excluded from the optimizer's default search** | Command Seal usage (`Action.useCommandSeal`) is implemented as a real, available action for Manual/Sandbox mode, but the optimizer/search (file 09 §4) should **not** default to spending one as part of a repeatable farming/clear strategy. **Confirmed by the project owner's direct gameplay knowledge**: the 3 real selectable effects are (1) fill one servant's NP gauge to 100% — cost 1 seal, (2) heal one servant's HP to 100% — cost 1 seal, (3) revive every dead party member (also maxing their NP gauge) — cost all 3 seals at once. (An earlier, incorrect guess in this doc — "guarantee the next card played" — is not a real effect and has been removed.) **Also confirmed by the project owner**: Command Seals reset **per day** (a daily allotment), not per battle/per account-wide slow regen as this doc previously assumed — a materially scarcer resource than "3 per account, slowly regenerating" implied, and the project owner's stated preference is to avoid relying on them for anything meant to be repeated (e.g. a 3T farm route run many times a day). | Relevant for the ST burst-finder / one-off "can I clear this at all" use case, where the user explicitly opts into spending a Seal — a real per-day resource worth spending on a single hard clear. **Not** relevant as an optimizer default: since Seals reset daily rather than per battle, a suggested strategy that assumes one is available every run would be unusable for repeated farming. The optimizer should treat Command Seal usage as an explicit, user-opted-in mode (e.g. "how do I clear this once, spending resources freely" vs. the default "sustainable, repeatable route"), not something it reaches for automatically. Command Seals are a **Master-level (account-wide) resource, not per-servant** — max 3 — the data model tracks one shared counter per `BattleState`, not one per `ServantInstance`. |
| **Critical hits/stars are fully modeled, including RNG** | Star generation per hit, star weight/absorption per servant, star carry-over cap, crit chance derived from stars-on-hand, and crit damage multiplier are all part of the core simulation, not deferred | Needed to compute genuine **probability of success** for a 3T line that isn't purely NP/skill-guaranteed damage (i.e. a plan relying partly on crits from Buster loops). This means the optimizer/simulator must support probabilistic outcomes (e.g. "87% chance to clear in 3T; falls to a safe 4T otherwise"), not just single deterministic damage numbers. |
| **Generalized N-wave / minimum-M-turn scope** | The engine targets "clear N waves in minimum turns" generically; 3T is just the common default target, not hardcoded | Real content varies (1-wave dailies, 4+ wave CQs); hardcoding "3 waves" anywhere in the data model or search logic would require rework later for non-3T use cases the user already anticipates wanting. |
| **Search scale: user-narrowed candidates + heuristic pruning** | The optimizer doesn't brute-force the user's *entire* roster (which can be hundreds of servants) unfiltered. Instead: (a) the user can pre-filter/shortlist candidate servants (e.g. by role, class, "servants I actually want considered") before a full search runs, and (b) the search itself uses heuristic pruning (discard combinations clearly far from viable early, rather than exhaustively simulating every possible skill-order/card-order permutation for every servant subset) | Full unfiltered brute-force over hundreds of servants × skill-order permutations × card-order permutations × RNG branching is computationally infeasible for a responsive tool. Narrowing + pruning keeps it tractable while still searching broadly enough to find non-obvious combinations — exact pruning heuristics to be designed in file 09, informed by which factors most decisively rule out a candidate early (e.g. insufficient total NP damage even before overcharge/crit is considered). |
| **Master level / party Cost budget is enforced** | The user's Master level determines a max party **Cost** budget; every servant and every CE has a Cost value (scaling with rarity/level), and a proposed party (6 servants + 6 CEs, since supports also cost Cost) must not exceed the user's current max Cost | This is a real, easy-to-forget constraint — a theoretically-optimal lineup (e.g. six 5-star NP5 servants with five-star BB CEs) may simply be unaffordable at the user's actual Master level. The optimizer must treat total Cost as a hard constraint, and the account data model must store the user's Master level (or directly their max Cost, if that's simpler to enter). |

## 4. Core Domain Concepts to Formalize

These are the building blocks the simulation engine must model. Each becomes (or feeds into) one of the research files in §5.

- **Damage formula**: base ATK, card modifier (Arts/Quick/Buster/Extra base multipliers), NP damage multiplier & overcharge scaling, class attack correction, class advantage/disadvantage triangle, attribute affinity triangle, buff-driven ATK%/NP damage%/special-defense-ignoring/piercing modifiers, defense-side DEF%/damage-cut/invincible/guts, crit modifier & crit stars, randomness (~0.9–1.1 variance band applied per hit), Overkill bonus modifier.
- **Hit count mechanics**: every card and every NP has its own **actual number of hits** (not a generic assumption — one servant's Buster card might be 1 hit, another's 3 or 5; one servant's NP might be 3 hits, another's 20+), plus a per-hit damage-distribution array (what % of the card's/NP's total damage lands on each individual hit). Both the hit *count* and the hit *distribution* are per-servant, per-card-type, per-NP data pulled from Atlas Academy (not derived or assumed). **Confirmed with live data by file 03**: `NiceServant.hitsDistribution` is an object keyed by card-type id, each value an array of per-hit damage percentages (e.g. one live example: Arts `[33,67]` 2 hits, Buster `[16,33,51]` 3 hits, Quick `[10,20,30,40]` 4 hits, Extra `[6,13,20,26,35]` 5 hits) — confirmed genuinely per-servant, not a shared default. `NiceTd.npDistribution` is the NP-equivalent array. Overkill is confirmed to be evaluated **per individual hit** in this array (a multi-hit card can have some hits overkill and others not, within the same action). — this matters independently of raw damage because NP refund is calculated **per hit** (more hits generally means more gauge gained from the same card, all else equal), crit stars drop **per hit**, and Overkill is evaluated **per hit** (not per card/NP as a whole) — so getting the hit count wrong silently breaks NP gauge, star, and overkill calculations even if the total damage number happens to look right.
- **NP gauge mechanics**: gauge gain from attacking, gauge gain from taking damage, gauge gain from skills/CEs (flat % charge), gauge consumption on NP use, gauge cap, Overcharge computed from gauge % at NP cast time. **Resolved by file 04**: both the attacking (`offensiveNPRate * (firstCardBonus + cardNpValue*max(1+cardMod,0)) * enemyServerMod * (1+npChargeRateMod) * criticalModifier`, then floored, then ×1.5 Overkill, then floored again) and defending (`defensiveNPRate * enemyServerMod * (1+npChargeRateMod) * (1+defensiveChargeRateMod)`, floored) NP-gain formulas are fully sourced from `fgo-docs`' `np.md`. **NP-gain rate is per-NP/per-servant (`NiceTd.npGain`), not a per-class table** — this corrects the original assumption below and in §6. **Neither formula has a class-triangle term** — class advantage never affects NP gain, confirmed on both the attacking and defending sides. Internal gauge unit: `NiceConstant.FULL_TD_POINT = 10000` = 100% gauge. **Overcharge is quantized into exactly 5 discrete integer stages (never interpolated)** — confirmed via the schema (`NiceFunction.svals`–`svals5`, `Vals.CheckOverChargeStageRange`), closing file 02 §6's fractional-OC-interpolation question (there is no fraction to interpolate; a cast NP always resolves at exactly one of 5 stage buckets). Per-NP gauge cost is a real per-NP field (`gaugeCount`, usually 1) rather than a hardcoded "always 100%." See `04-np-gauge-and-refund.md` for full detail, worked example, and remaining open edge-cases (exact stage-boundary rounding rule; `NP_DOUBLE_BURST`/`NP_TRIPLE_BURST` constants' purpose).
- **Buff/debuff system**: buff types (ATK up, DEF down, NP damage up, NP gain up, crit damage up, card-type-specific up, debuff resistance/success rate, taunt/guts/invincible/evade, field-specific, trait-granting), stacking rules, duration (turns vs "until next attack" one-shot consumption), targeting (self/single ally/all allies/single enemy/all enemies/random), conditional application via trait checks and individuality checks, buffs that grant/remove traits temporarily, "field" buffs (Sky/Land/Sea-type battlefield bonuses). **Fully resolved by file 05**: every numeric buff resolves through one shared "buff action" arithmetic (additive sum of `plusTypes`/`minusTypes` contributions, then clamped by `maxRate`/`limit` — file 02 §3, restated in file 05 §2). Two *independent* stacking mechanisms exist: (a) additive-within-action (§2, always applies to numeric buffs) and (b) **unstackable `buffGroup`** — buffs sharing the same non-zero `buffGroup` can't coexist (e.g. Petrify/Stun sharing group 500; `buffGroup` 0 = always stackable, used by most "Buster Up" buffs) — confirmed against the official `fgo-docs` site's "Unstackable buffs" section and live-verified this session (Cú Chulainn's Evade = `buffGroup` 200, Heracles' bond-CE Guts = `buffGroup` 600, matching the doc site's own cited examples exactly). Conditional/trait-gated buffs are confirmed structurally via `NiceBuff.ckSelfIndv`/`ckOpIndv` (live example: Dobrynya's "STR Up vs. Dragon" buff, gated by `ckOpIndv: [dragon]`) plus a richer set of `BuffScript` conditional fields (`HP_LOWER`/`HP_HIGHER`, `INDIVIDUALITIE_COUNT_ABOVE/BELOW`, `CheckOpponentBuffTypes`). Duration/consumption is governed by up to three independent expiry axes per buff instance: `Turn` countdown, `Count` (use-based) countdown, and external dispel — see `05-buffs-and-debuffs.md` §7 for the consolidated model, and §6 for concrete `Turn`/`Count` field values live-verified for Evade/Guts/Invincible.
- **Trait (individuality) system**: every servant/enemy/card has a trait list; many buffs/debuffs/NP effects only apply if the target has (or lacks) certain traits (e.g. "vs Male," "vs Divine," "vs Poisoned," "vs Servant," "vs EA class"); some skills add temporary traits to self or enemies (curse marks, "King Proteus," "Bazett's Black Keys equip," etc.) that unlock other conditional effects — this is the mechanism the generic engine must support rather than special-casing. **Resolved by file 06**: traits are a fixed, closed enum (375 named values, schema-confirmed) wrapped per-instance as `NiceTrait {id, name, negative}`. Confirmed field/terrain buffs (Sky/Land/Sea etc.) are literally implemented as traits on the battlefield (`fieldForest`/`fieldHeaven`/`fieldBurning`/etc.), checked with the same `ckSelfIndv`/`ckOpIndv` machinery as any unit trait (file 05 §4) — no separate "field" subsystem needed. Also confirmed some traits are purely a single servant's private state-machine hooks (e.g. Kingprotea's `kingproteaGrowth`/`kingproteaProliferation` family) — a reusable pattern for modeling any servant's internal "stacks" mechanic as trait-grant-and-count rather than a bespoke counter. **Temporary trait grants**: `addIndividuality`/`subIndividuality` are confirmed real `NiceBuffType`/`NiceFuncType` values (schema-level), using the same duration model as any other buff (file 05 §7). **Live example found (follow-up pass)**: Romulus=Quirinus's Skill 1 grants enemies the `roman` trait for 5 turns via `addIndividuality` — see file 06 §2 for full detail.
- **Multi-function skills/NPs (independently-gated effect list)**: a single skill or NP is not one effect but an **ordered list of separate functions**, each with its own target, value, and (crucially) its own independent trait/condition gate — they don't all share one on/off switch. Two concrete patterns the engine must support natively, not as special cases:
  - **Skill with a mix of unconditional + trait-gated buffs in the same activation** (cited example: Koyanskaya of Light's skill grants a general buff unconditionally *and* a separate, larger buff that only applies "vs Male" targets) — i.e. one skill press can produce two different functions, one always-on and one trait-filtered, stacking together against a qualifying target.
  - **NP whose own damage-multiplier function is itself trait-conditional** (cited example: Euryale's NP deals bonus/scaled damage specifically when the target has the Male trait) — here the trait check isn't gating a *separate* buff, it's gating (or scaling) a term **inside the NP's own damage function**, so the damage formula (file 02) must support "this multiplier only applies / is a different value if target has trait X" as a native input, not just external buffs modifying an otherwise-fixed NP multiplier.
  - **NP whose effective damage scales with Overcharge via an earlier self-buff function, not via the damage function itself** (live-verified example: Space Ishtar's NP "Edin Shugurra Quasar" — function 0 grants a self `upNpdamage` buff worth +20%/+30%/+40%/+50%/+60% at OC1–OC5, function 1 is the actual `damageNp` hit, whose own base multiplier is identical across all OC levels and only varies by NP level). This is the same "ordered list of functions" structure as the other two patterns, but the conditioning variable is **function execution order within the same skill/NP**, not a trait check — see "Intra-skill/NP function execution order" below.
  - Both patterns confirm the engine's function/buff model needs, per function: a target-trait condition, and support for a function that changes its own base value (not just adds a stackable buff) based on that condition — this should be checked against how Atlas Academy actually encodes it (`functions[].funcquestTvals`/`svals` vs a target's `traits`, need to confirm exact field names in file 01).
- **Class/attribute system**: 3-class-triangle attack multipliers, per-class base "class attack rate" (Saber/Berserker etc. have different baseline multipliers), attribute (Man/Earth/Sky/Star/Beast) triangle multipliers, and how they compose with class advantage multiplicatively. **Per-class NP-gauge generation rate table question resolved as moot by file 04**: there is no such table — NP gain is per-NP/per-servant (`NiceTd.npGain`), and neither the attacking nor defending NP-gain formula has a class-triangle term at all (confirmed both directions). **Class attack rate and class triangle fully resolved by file 06** with live-fetched tables: `NiceClassAttackRate.json` gives a flat per-class multiplier (e.g. Berserker/Ruler/Avenger = 1100, Archer/Caster/Assassin < 1000, most others = 1000); `NiceClassRelation.json` is a **full N×N matchup matrix**, not a simple 3-way cycle — confirmed exceptions include **Shielder being the one class that does NOT get bonus damage vs. Berserker** (1.0× vs. everyone else's 2.0×) and **Avenger dealing 2.0× to Ruler** while most other non-triangle classes deal only a neutral 1.0×. **Attribute triangle fully resolved**: `NiceAttributeRelation.json` confirms Human→Sky→Earth→Human as a true 3-way win/lose cycle, but **Star↔Beast is a different shape — a mutual bonus pair** (both directions deal 1.1×, not a win/lose relationship) — this asymmetry in relationship *type* (cycle vs. mutual-bonus) was not previously documented anywhere in this project. Both class-triangle and attribute-triangle are confirmed **always-applied, independent multiplicative terms** (file 02) — composition question closed. See `06-traits-and-class-mechanics.md` for full tables and the `overwriteBattleclass`/`overwriteClassrelatioAtk`/`overwriteClassrelatioDef` buff-type family (mid-battle override mechanism, now with two live examples found: Sima Yi (Reines)'s NP for the relation-value-override variant, Kazuradrop's Skill 3 for the effective-class-swap variant — file 06 §4).
- **Mystic Code mechanics**: **resolved by file 07**. A Mystic Code is just 3 active skills using the exact same `NiceSkill`/`NiceFunc`/`NiceBuff` engine as servant skills (no separate MC-only mechanic taxonomy). Live survey of all 28 currently-known MCs (JP) found the skill pool draws from a small recurring set of `funcType` categories: `addStateShort`/`addState` (turn- vs count-limited buffs, self/ally/party), `gainHp`, `gainNp`, `gainStar`, `addState` targeting `enemy` (debuffs — e.g. Gandr's Stun), `subState` (cleanse), `shortenSkill` (cooldown reduction), `delayNpturn` (push back enemy NP turn), and `cardReset` (re-draw the current 5-card hand, e.g. Mage's Association Uniform's "Command Shuffle"). **Order Change** (`funcType: replaceMember`, targets one selectable sub-member) exists on only 3 of the 28 MCs (Chaldea Combat Uniform id 20, Chaldea Uniform - Decisive Battle id 210, Normal Chaldea Uniform id 440), always as the 3rd skill slot, cooldown 15→13 turns across levels 1-10. **State-transfer rules on swap — resolved by the project owner's direct gameplay knowledge (follow-up pass)**: a servant swapped to the backline has its entire state **frozen** — buffs/debuffs (`Turn`/`Count` unchanged), skill cooldowns, HP, and NP gauge all stop advancing while benched, and resume from exactly the same state the moment it's swapped back in. This resolves the wiki-tier sources' ambiguity (Fandom/GamePress's "remain static" phrasing could have meant "keep ticking" or "freeze," and didn't address HP/NP at all) firmly in favor of freeze. See `07-mystic-codes.md` §4 for full detail.
- **Enemy mechanics**: **resolved by file 08** (except the AOE/overkill-per-target interaction, still tracked separately below). "Enemy rank (Bronze/Silver/Gold)" turned out to have **no matching mechanic in any primary or Kyte-tier source** — the only schema hit for those three words is `NiceItemBGType`, a material drop-icon background color, unrelated to enemies. The real, confirmed per-enemy NP/star-gain modifier is **`EnemyServerMod`** (`tdRate`/`tdAttackRate`/`starRate`, per-mille, read directly per enemy record from live quest data — e.g. a live-fetched training quest showed `tdRate:1200` i.e. a deliberate +20% NP-gain boost for that quest's mobs) — confirmed to vary per-enemy-per-quest, **not** derived from `EnemyRoleType` (`normal`/`danger`/`servant`) or any fixed 3-tier table (a `danger`-role enemy in the same live wave had identical `serverMod` to the `normal`-role enemies beside it). Enemy traits use the exact same closed 375-value `Trait` enum as file 06 — no enemy-specific extension. Debuff/instant-death resistance is governed by explicit toggle flags on the applying function (`UseSvtResistRate`/`UseBuffResistRate`/`IgnoreResistance`) plus a `deathRate`/`instantDeathChance` base stat and matching `upResistInstantdeath` buff type — "immune to X" is the general resistance formula (file 05 §4) with a large-enough resistance value, not a hardcoded immunity flag. "Break Bar"/gauge-break is **confirmed to be the exact same mechanism as multi-bar HP** already resolved by file 01 — Atlas Academy's own schema names the `shift` field "Break bar switch to these NPC IDs," so no separate data structure is needed beyond the "wave = list of enemy records, `shift`/`call` swap in another one" model already decided. See `08-enemy-mechanics.md` for full detail and remaining open items (live `shift` example not captured; `criticalRate`/`recover` numeric effects not traced).
- **Card mechanics**: Quick/Arts/Buster/Extra Attack base modifiers, brave chain bonus (3-of-a-kind same type), chain order bonus (first/second/third card position multiplier), Mighty Chain / all-5-star-card considerations, NP card follow-up mechanics, critical star generation/absorption, "extra attack" triggered after chain.
- **Level-scaled stats**: servant ATK/HP and CE ATK/HP are not flat values — they grow per level (and jump at ascension breakpoints for servants). The engine must interpolate/derive the correct ATK/HP at the user's actual entered level+ascension (servant) and level (CE), using Atlas Academy's per-level growth data, rather than defaulting to max-level figures.
- **Level-scaled skill & append skill effects**: each of a servant's 3 active skills and each equipped append skill has its own independent 1–10 level, and the effect values (`svals` — e.g. how much ATK% a buff grants, how much NP% a charge skill gives, a debuff's %chance/potency) scale per that skill's own level, not the servant's overall level. A servant can be Lv.100 with Skill 1 at level 10 but Skill 3 still at level 6, and the two skills must be evaluated at their own actual levels independently — same "use the real account state" principle as NP level, Rank-Up toggles, and CE MLB state.
- **CE Limit Break scaling**: a CE's skill effect values can differ between base (unbroken) and MLB (max limit broken) state; some CEs also change effect values across intermediate LB steps. The engine needs the per-LB-step value table per CE and the user's stored MLB/LB-count flag per equipped copy.
- **CE ownership as inventory (multiple copies)**: unlike servants (each owned once, differentiated only by NP level for duplicates), CEs are held as a quantity — the optimizer's party-builder must track how many copies of each CE the user owns and never propose equipping more simultaneous copies across the party than that count allows, with each individual copy potentially at a different level/LB state if the user entered them separately.
- **Advanced/manual override mode**: beyond the normal "compute everything from selected skills/CEs/buffs" pipeline, the engine should expose a layer where any individual computed term (e.g. total ATK%, NP damage%, class correction, target's DEF%, card multiplier) can be manually pinned by the user, overriding the computed value for that calculation only — useful for validation, unmodeled mechanics, and what-if exploration.
- **Critical stars & critical hits**: star generation per hit (varies by card type/position, buffs), star absorption/weight per servant (affects who "owns" stars carried into next turn), stars carried-over cap (commonly 9/10), critical chance derived from stars-on-hand, critical damage multiplier (base 2x + buffs), and how crit interacts with NP cards (NP cards themselves are not crit-able in the normal sense — needs confirming) and with card chains (does a Buster crit change chain bonus math?). **Partially resolved by file 03**: the star-*drop* (generation) formula is fully confirmed from primary source (`baseStarRate` = `NiceServant.starGen`, plus per-card-type/position `addCritical`/`adjustCritical` from `NiceCard.json`, plus buff actions, plus a flat +20pp bonus on crit hits and +30pp on Overkill hits) — this is a genuine per-hit probability, not a fixed yield, confirming the RNG-based probability-of-clear approach is required exactly where file 00 already assumed. Base critical damage multiplier **is** confirmed: exactly 2.0x (`NiceConstant.CRITICAL_ATTACK_RATE`), with "+buffs" applying through a separate, additive buff-action term in the damage formula (file 02). Also confirmed: **NP cards carry no `NiceCard.json` entry for critical-related fields at all** (an all-zero stub), consistent with (but not an explicit primary-source statement of) "NP cards cannot crit." Also confirmed: Overkill does **not** directly multiply raw hit damage in the formula itself — it only affects NP gain (×1.5) and star drop (+30pp). **Crit-chance-from-stars-on-hand substantially resolved by file 04**: `NiceConstant.CRITICAL_RATE_PER_STAR = 100` (→ 10% crit chance per star allocated to a card) is a genuine primary-source constant (not just community folklore as previously flagged) — confirmed against the official `fgo-docs` site's own description of the mechanism (stars-on-hand allocated per-card, driving crit-chance) and against a datamined mechanism write-up (same `blogs.nrvnqsr.com` author/network `fgo-docs` itself cites for `np.md`/`critstars.md`): each landed hit's stars are allocated one-by-one to the 5 hand cards via a weighted lottery (per-servant `criticalWeight` + a shuffled +50/+20/+20 base-slot bonus + any Star Focus buff), and each star allocated to a card adds +10% (currently; a 2015 measurement found +11%, consistent with the constant having been tuned since) crit chance to that card, capped at 100%. **Resolved by a follow-up pass**: the "stars-carried-over-to-next-turn cap" question was mis-framed — stars don't accumulate past one turn (a turn's stars determine the *next* turn's crit chances via the weighted lottery, then are discarded, not banked further), so no cap constant is needed; the commonly-cited "9/10" was a conflation of the (separately confirmed) 10-stars-per-card and 50-stars-for-all-5-cards single-turn figures. `criticalWeight`'s schema location is also resolved: it's `NiceServant.starAbsorb` on the `/nice/` endpoint (same value as `mstSvtLimit.criticalWeight`, live-verified equal on Mash). See `04-np-gauge-and-refund.md` §6.3 for full detail and citations.
- **Debuff application: success rate & resistance**: debuffs (unlike buffs on your own side) have a base application chance that can be boosted by "debuff success rate up" and reduced by target's "debuff resistance," with "certain success" (guaranteed-hit) effects bypassing resistance entirely. This directly matters for the user's point about ST/AOE debuff usage — the engine needs to model chance-of-landing, not just "assume debuff always applies." **Resolved — application-check formula sourced from the official `fgo-docs` site** ("How MISS and GUARD are determined"): `num2 = target's resistance + random_roll[0,1000)`; if `num2 > chance` the debuff fails (displaying GUARD if `num2 > 1000`, otherwise MISS — a purely cosmetic distinction); otherwise it lands. A 100%-chance debuff can still visually show as GUARD on a failed roll, never MISS. The "certain success"/Sure-Hit mechanism that bypasses this check entirely (referenced in Invincible's own detail text, "Ignore Sure Hit") is **resolved by file 05 §6.3**: it's `breakAvoidance`, a dedicated attacker-side `NiceBuffType`, narrower in scope than `pierceInvincible` (Evade-only vs. both Evade+Invincible) — confirmed against the project owner's direct gameplay experience.
- **Buff stacking caps/limits**: some buff categories may have a hard ceiling regardless of how many sources stack. **Resolved by file 02**: the "buff action" system sums all same-action buffs additively (as integers) then clamps the total by that action's `maxRate` (defined per-buff, in `NiceBuff.maxRate` per file 01) — additive stacking within an action, with a per-action hard ceiling, not unlimited additive and not multiplicative-per-source. See `02-damage-formula.md` §3 for the exact pseudocode.
- **Overcharge range beyond the "normal" 100–300%**: while base NP gauge caps at 300% (OC3) for most servants, certain servant kits/CEs can push effective Overcharge further (e.g. OC4/OC5) via special skills — the engine's OC handling must not hardcode a max of 300%. **Resolved by file 02**: confirmed at the schema level — `NiceFunction` has explicit `svals4`/`svals5` fields (OC4/OC5 value tables) alongside `svals`/`svals2`/`svals3` (OC1–3), so the engine should always check for OC4/5 presence rather than assuming 3 brackets. Also confirmed via a **live-verified real example (Space Ishtar's NP, id 1100901)**: her damage-dealing function's own base multiplier is byte-identical across OC1–OC5 (only NP level changes it) — yet her NP's *effective* damage genuinely does increase with Overcharge (+20%/+30%/+40%/+50%/+60% at OC1–5), because an **earlier function in the same NP's function list grants herself a self "NP damage up" buff that scales with OC**, and that buff is already active by the time the later damage function resolves (functions execute in array order within one NP/skill activation — see the new "intra-skill/NP function execution order" domain concept below). **Net implication: the engine cannot check "does the damage function itself have OC-scaled svals" and stop there** — it must evaluate every function in a skill/NP's `functions` array in order, applying each one's effects (including self-buffs) before evaluating the next, or OC-driven damage increases built this way (a common competitive-kit pattern, not a one-off) will be silently missed. Exact fractional-OC interpolation rule (between adjacent OC brackets) is still an open item, deferred to file 04.
- **Field/terrain (Land/Sky/Sea/Underground, etc.)**: this is a property of the **quest/wave itself** (not of an enemy or servant) that some buffs/debuffs/NPs key off ("ATK up in Sky-attribute fields," etc.) — needs to be part of the wave/quest config, separate from per-enemy trait data.
- **Command Codes (CC)**: equipped per-servant, can grant extra crit stars, flat NP gauge, damage, or buffs when that servant's card is played/NP is used — an additional per-servant loadout layer beyond skills/CE/Mystic Code that the account data model should include.
- **Enemy reinforcement / spawn-on-death**: some CQ/event bosses trigger a new enemy (reinforcement, "true form" enemy swap, or a previously-hidden unit) appearing after a specific enemy in the wave dies, or after some other trigger (turn count, HP threshold/gauge break). The wave/quest data model needs to represent this as a conditional spawn rule, not just a fixed enemy list, so multi-turn setup plans (see Goal §5) that deliberately kill enemies in a specific order can be modeled and their consequences simulated. **Resolved by file 01 research**: Atlas Academy models this directly via the enemy's `call` field ("summon these NPC IDs" — a full separate enemy record already present in the quest's data, not something the app has to invent). This is the same mechanism as multi-bar HP below, just triggered by death/turn/threshold instead of "this bar emptied."
- **Self-damage / HP-cost NPs and skills**: some servants deal damage to themselves (or allies) as part of their own NP/skill effect (e.g. paying HP for a stronger effect) — while this project doesn't simulate *enemy* attacks against the player, self-inflicted HP costs from the player's own kit still need tracking since they can trigger Guts, HP-based conditional buffs, or servant death mid-simulation.
- **Per-enemy configuration**: each enemy is its own unit record (HP, class, attribute, traits, base defense%, active buffs/debuffs list, rank) inside a wave's enemy list — waves are a collection of independent enemy units, not a single aggregated stat block, since real fights can have mixed buffed/unbuffed enemies within the same wave.
- **Overcharge and "consume-once" buffs**: some skills/CEs grant an Overcharge-level buff (raises the NP's effective overcharge for its next cast) or other stackable-looking buffs that are actually **single-use** — they have a multi-turn duration window (e.g. active for 3 turns) but are consumed/expire after being *applied once* (typically on the next NP cast or next attack), not after every attack within that window. The engine must model a buff's "uses remaining" (consumption count) as a separate property from its "turns remaining" (duration), since a buff can end for either reason first.
- **Conditional/triggered buffs**: some buffs only take effect when a specific condition is met at resolution time, not unconditionally for their whole duration (the user cited Aesc/Ashiiya-Aescetica-type kits as an example — buffs that activate only if e.g. a certain card type is played, a certain ally/enemy state exists, or a prior effect procced). These need to be modeled as conditional functions (predicate + effect), not flat always-on modifiers, mirroring how Atlas Academy's function `condition`/`cond` fields likely encode them.
- **NP/skill changes from Rank-Up Quests & Interludes**: many older servants have had their NP (or skills) upgraded via a Rank-Up Quest (called "Strengthening Quest"/"NP Upgrade" in some sources) or unlocked/modified via Interlude — changing hit-count, damage multiplier, overcharge behavior, or adding an entirely new effect to the base NP/skill. Since the user's own account may or may not have actually cleared that Rank-Up/Interlude quest yet, this must be a **per-servant, user-set toggle** ("has this NP/skill strengthening been unlocked on my account? yes/no") reflecting the real account state — not an assumption that the current/upgraded version always applies. The engine needs both the pre-strengthening and post-strengthening NP/skill definitions available (if Atlas Academy exposes historical versions) so it can compute damage using whichever the user actually has unlocked.
- **Passive/innate skills — three distinct categories, not one, and NOT purely class-tied**: every servant has always-active passives that must be included by default (not just the 3 chosen active skills + NP). **Live-verified via Space Ishtar's data + official schema descriptions**, there are three separate fields, each meaning something different: (1) `classPassive` — official description is simply "list of servant's passive skills," and despite the field's name, this list is a **mix** of genuinely class-shared skills (Magic Resistance, Independent Action — same skill ID/name reused across many servants of a class) **and per-servant-unique innate passives that happen to live in the same list** (Space Ishtar's own `classPassive` includes "Avenger EX" → grants herself an always-on **NP Gain Up When Damaged** buff, and "Self-Restoration (Magical Energy) B" → grants **NP Gain Each Turn** — neither of these is shared by other Avenger-class servants; they're her own kit). **This directly matters for NP gauge modeling (file 04)**: these passives grant buffs through the exact same `functions`/buff-action pipeline as active skills and NPs (e.g. the `dropNp`/NP-gain-up buff action from file 04 §1), so the engine's default per-turn NP-gain calculation must scan a servant's full `classPassive` list for NP-gain-affecting functions, not just their 3 active skills — a servant can have significant passive NP generation the player never "activates." (2) `extraPassive` — official description: "extra **event** passive skills (bond bonus, damage bonus, etc.)" — these are only relevant/active during specific limited-time events, not permanent, and should not be included in a general damage/NP calc by default. (3) `appendPassive` — servant-independent purchasable Append Skills (a separate unlock system, `appendSkillMaterials`-gated); empty for many servants (confirmed empty for Space Ishtar) and structurally more like a 4th selectable skill slot than a true always-on passive — needs its own dedicated look (deferred; not urgent for files 04-08).
- **Card draw / hand mechanics (RNG surface for probability modeling)**: each turn the game deals a hand of 5 cards drawn from the fielded 3 servants' decks (5 cards each, so 15 possible), with any servant whose NP gauge is full always having their NP card appear in addition; the specific 5 non-NP cards shown are randomized (with game-side weighting/guarantees, e.g. typically at least one of each card type appears though this needs sourcing) and the player picks 3 to play. This randomness in *which cards are available to pick from* is a distinct RNG source from crit stars and is essential to modeling "probability of achieving a specific chain" (e.g. probability of drawing a Buster brave chain) for the 3T success-probability feature.
- **Front-line vs sub-member (back line) party structure**: a party has 3 active (front-line) servants and up to 3 sub-members (back line) who cannot act but can be swapped in via death-replacement or Order Change; some skills/CEs can target sub-members (e.g. buffing/charging NP on a benched servant pre-emptively) — the engine's targeting logic must distinguish "any ally" (front+back) from "active ally" (front-line only) skill ranges.
- **"Start of quest" pre-battle buffs**: certain CEs (e.g. NP-gauge-at-start CEs), support servant skills usable before the fight begins ("start the quest with X% NP charge"), and some Mystic Codes apply their effect once at quest start rather than on-demand mid-battle — the engine needs a distinct "pre-battle setup" phase separate from Turn 1's normal skill/card actions.
- **Enemy special resistances / damage-nullifying quirks**: beyond generic DEF% and buff-based invincibility, some enemies have specific immunities or unusual defensive rules (e.g. instant-death immunity — nearly universal for story-relevant enemies, specific debuff-type immunities noted via trait, or a scripted "reduce all damage taken to 1" state on some meme/quest gimmick enemies) — the per-enemy config (see below) should allow flagging these rather than assuming all enemies behave like a plain HP+DEF% bag.
- **Buff/debuff removal (dispel) and invincibility-piercing**: some player skills/NPs remove an enemy's existing buffs (dispel) or remove an ally's own debuffs — the engine must support mid-simulation removal of a previously-applied buff/debuff, not just addition (directly relevant to the per-enemy manually-added buffs described above, e.g. dispelling a self-buffed DEF-up before attacking). Separately, some NPs/skills explicitly **ignore/pierce Invincible** (deal damage through an invincibility buff that would otherwise reduce the hit to 0) — this must be modeled as a property of the attacking function ("ignores invincible: yes/no"), not just a property of the defender's buff, since the same invincible enemy can be hit-through by one attacker's kit but not another's. **Resolved by file 05**: dispel is its own `NiceFuncType` family (`subState`, `releaseState` — exact distinction between the two not yet pinned down), targeting existing buffs **by trait**, matched against each buff's own `vals` trait list (confirmed by that field's own schema description: "buff removal uses this field to target the buffs"). Invincible-piercing is confirmed structurally separate from dispel: `pierceInvincible`/`pierceSpecialInvincible`/`breakAvoidance` are attacker-side buff types checked at damage-resolution time, not removal effects. `BuffScript.NotPierceIndividuality` lets a specific Invincible/Evade instance declare itself immune to piercing from attacks with certain traits (schema-confirmed, no live example yet).
- **Evade vs Invincible are distinct buff types, and piercing them requires a specific attacker-side capability, not a generic override**: Evade (dodge the incoming hit/attack entirely — the attack doesn't connect at all, so it typically also yields **no** NP gauge/crit-star gain from that action) is mechanically different from Invincible/damage-cut-to-zero (the hit still "connects" for gauge/star/on-hit-trigger purposes but deals 0 damage) — the engine must model them as separate buff types with separate downstream consequences, not one generic "damage nullified" flag. Both come in **two distinct expiration models** that the engine must tell apart per buff instance (not assume one or the other): a **count-based** type (expires after absorbing N hits/attacks, however many turns that takes — could be used up within a single turn if hit N times, or could last several turns if the target isn't attacked) and a **turn-based** type (simply lasts a fixed number of turns and applies to every qualifying hit during that whole window, not consumed per-hit at all). This is a genuinely different expiration rule, not just "count vs duration as two properties of the same buff" — a given evade/invincible buff is fundamentally *one or the other* kind, and the engine needs to read which from the source data rather than defaulting to either. **Strategic implication the optimizer/sandbox must be able to represent**: against a count-based Evade/Invincible, a valid and often-necessary plan is to deliberately spend earlier cards/attacks (from the same or other servants) purely to *bait and burn down* the remaining count, then land the real NP/burst only once the buff is exhausted — this means the simulator's action-sequencing must let the user (or the optimizer's search) order "sacrifice" attacks before the "real" damage action within the same turn or across turns, and correctly track the buff's remaining count decrementing hit-by-hit as those sacrifice attacks land. **Resolved by file 01 research**: the count-vs-turn distinction is encoded as two separate, independently-nullable fields (`Turn` and `Count`) on the same buff-value object — a buff instance is read as turn-based if `Turn` is set and `Count` is null, count-based if `Count` is set, confirming this must be checked per buff instance rather than assumed from the buff's type name alone. Both types can also be conditionally scoped (e.g. "invincible against Buster cards only," "evade vs NP only," "invincible except vs NPs") — meaning whether a given attack bypasses them depends on **both** (a) the specific buff's own scope/condition and (b) whether the attacking skill/NP separately carries an explicit ignore-invincible/ignore-evade capability (a property the servant's own kit must have — not something the player can apply generically at will, and not every "high damage" NP automatically pierces just because it's strong). This pairing (defender's buff condition × attacker's specific piercing capability) needs to be modeled as two independent checks that both matter, not collapsed into one. **Live-verified with real field values by file 05**: Cú Chulainn's Evade = `Turn:-1, Count:3` (count-based, `-1` is the "unlimited on this axis" sentinel); Nero Bride's NP Invincible = `Turn:1, Count:-1` (turn-based) — confirming both predicted shapes occur in real data and that `-1` (not null) is the actual "unlimited" sentinel value on the populated axis. **Both resolved by file 05, after further passes**: "Sure Hit" is `breakAvoidance`, a dedicated attacker-side `NiceBuffType`, Evade-only in scope (narrower than `pierceInvincible`, which pierces both Evade and Invincible) — see file 05 §6.3 for the full priority-ordered piercing model (including the `specialInvincible`/`pierceSpecialInvincible` "anti-purge" tier, live-confirmed via Artoria Caster/Avalon le Fae and Altria Caster (Berserker)'s NPs). And confirmed via the project owner's direct in-game observation: both an Evaded and an Invincible-blocked hit still generate NP gauge and crit stars normally for the attacker — only the damage-formula output itself is zeroed by either buff (file 05 §6.4).
- **Multi-bar/segmented enemy HP — distinct from Guts**: some enemies (especially raid-style bosses) have HP split into **multiple sequential bars** shown as one continuous fight rather than a single pool — depleting one bar transitions to the next rather than ending the fight, and each bar can have its **own defense%/resistances/buffs/traits** different from the others (not just the same enemy with more HP). This is mechanically distinct from Guts (which is a full death-and-revive with a gap, not a segmented continuous bar) and from the "Break Bar"/gauge-break mechanic already noted (which is usually about interrupting an enemy's NP charge/turn rather than being a literal separate HP segment, though the two can co-occur on the same boss). **Resolved by file 01 research — and the answer changes the data-model shape**: Atlas Academy does **not** encode this as one enemy record with an array of HP segments. Instead, **each bar is a fully separate enemy record** (its own HP/DEF%/traits/buffs, already present in the quest's data) linked via a `shift` field on the current bar ("switch to this NPC ID when I hit 0 HP, instead of dying"). This is the *same* underlying mechanism as enemy reinforcement/spawn-on-death above — the only difference is the trigger (bar-empty vs. death/turn/threshold). **Practical consequence: no bespoke "multi-bar" structure is needed in the engine.** The already-decided "wave = list of independent enemy unit records" data model (§3 Key Decisions) already covers this — the simulator just needs one additional event type: "this enemy hit 0 HP and has a `shift` target → swap in the next enemy record instead of ending the wave," which is the same event type needed for `call`-triggered reinforcement.
- **Guts (revive-on-death) — matters even in damage-only scope, not just survivability**: Guts revives a unit with a specific amount/percentage of HP (and sometimes temporary invincibility/buffs) the moment they'd otherwise die, and typically has a **count** (number of revives) separate from its turn duration — same count-vs-turn distinction as Evade/Invincible above. Critically, **enemy-side Guts is a core-scope concern regardless of whether player-survivability simulation ends up in scope**: many bosses/CQ enemies have Guts, meaning "enough damage to bring HP to 0" is not the same as "enough damage to actually finish them" — the real lethal-damage target must clear the *combined* HP across the Guts revival(s) (first HP bar + revived HP amount, possibly multiple stacked Guts), or the plan must specifically account for a follow-up hit/turn to finish the revived sliver. The ST burst-finder (Goal §2) and ST oneshot planning in particular must treat enemy Guts as a hard threshold to check against, not just raw current HP. Player-side Guts (on the user's own servants) matters separately for self-damage NPs/skills (already noted above) and, if survivability simulation ends up in scope, for surviving lethal enemy hits. **Resolved by file 01 research**: Guts is not a separate enemy-record field — it's a normal buff (`NiceBuffType` includes `guts`/`gutsRatio`/`upGutsHp`/`downGutsHp`/`shiftGuts` and related variants), granted via the enemy's passive skills or NP/skill functions like any other buff. This means enemy Guts is **auto-detectable from real data** (scan the enemy's passives/functions for a guts-type buff, read revive count and HP amount from that buff instance's value fields) — no manual per-quest entry needed for quests the API has enemy data for. **Live-verified by file 05**: Heracles' bond-CE Guts = `Turn:-1, Count:3, Value:500` — 3 revives, each restoring to 50% HP (`Value` uses the same per-mille scaling as every other buff-action value in this project, 1000=100%), confirming both the count-based-with-unlimited-turn shape and the HP-restore-amount field location (`Vals.Value`).
- **Same-turn NP-order effects (multi-NP chain interactions)**: when multiple NPs are cast in the same turn (a common 3T-farm pattern — e.g. a support's buff-granting NP cast first, then the attacker's damage NP cast second within that same turn), the buffs applied by the first NP must already be active when the second NP's damage is calculated. The turn-by-turn simulator must resolve actions **strictly in the order the user/optimizer sequenced them within the turn**, not all-at-once, so this kind of intra-turn buff-into-NP cascading (which is central to how burst/ST damage chains are actually built in-game) works correctly.
- **Intra-skill/NP function execution order (a finer-grained version of the above, confirmed via file 02's live Space Ishtar lookup)**: this is the *same* ordering principle, but one level more granular — it applies **within a single skill or NP's own `functions` list**, not just across separate skill/NP casts in a turn. A skill/NP's functions execute strictly in array order, and an earlier function's effect (typically a self-buff) can already be active by the time a later function in the *same* activation resolves — this is the actual mechanism behind NPs whose effective damage scales with Overcharge without the damage function itself being OC-scaled (see the Space Ishtar example above): an earlier function grants an OC-scaled self "NP damage up" buff, and the later damage function benefits from it because it resolves second. **Engine implication**: the function evaluator must process one skill/NP's `functions` array sequentially, re-checking buff state before each subsequent function — it cannot evaluate all of a skill/NP's functions against one buff-state snapshot taken at the start of that skill/NP's resolution, or effects like this will be silently missed. **A second corroborating example (follow-up pass, project owner's recollection)**: Taira-no-Kagekiyo's NP (`GET /nice/JP/servant/1101000`) orders its functions `subState` (strip every enemy buff carrying the `buffPositiveEffect` trait) → `damageNpIndividualSum` (the damage) → `addState` (Curse) — the dispel is fully resolved *before* the damage function runs, not merely "the same activation," confirming this isn't a self-buff-only pattern (research/05 §5 has the full detail).
